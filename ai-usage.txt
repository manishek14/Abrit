AI Usage Disclosure — AbrIT Ticketing System
=============================================

As explicitly allowed and encouraged by the AbrIT trial assignment, this
project was developed with AI assistance. This file documents the tools used,
for what, and includes sample prompts. Full transparency — no credentials were
ever shared with or generated by the tools, and no API quota was spent while
Telegram/OpenRouter keys were empty.

Tools & models
--------------
- GLM (Z.ai) agent — main implementation partner for the entire repository:
  architecture review of the provided execution-plan PDF, backend code
  (NestJS/TypeORM/PostgreSQL), Telegram & AI integration layers, tests,
  docs, Git workflow, and verification of every phase against a REAL
  PostgreSQL instance before each commit (boot smoke tests, functional
  webhook runs, live websocket browser checks).
- Frontend (React + Vite + Ant Design + TanStack Query + Socket.IO) was
  implemented by a delegated sub-agent (also GLM) against a precise API
  contract written by the main agent, then reviewed, rebuilt and functionally
  verified end-to-end in a real browser session by the main agent.
- Model actually used for implementation: GLM (Z.ai sandbox agent).

What the human owner did
------------------------
- Reviewed and approved the execution-plan PDF and defined all product
  decisions: removal of Redis/BullMQ for v1, separate `chat_id` column, final
  bot command set (/start /new /status /close /help), WebSocket requirement,
  bilingual README, phase-by-phase push/verify workflow.
- Instructed that external APIs (Telegram/OpenRouter) stay DISABLED with empty
  credential slots until further notice — the modules are fully implemented
  and activate by configuration only.
- Will supply the real credentials and run the two remaining manual
  scenarios (real bot conversation, real OpenRouter multi-turn check).

Sample prompts (translated from Persian)
----------------------------------------
- "Review the execution-plan PDF against the company's task PDF, adopt my
  corrections, then implement Phase 0: repository structure, NestJS with
  fail-fast env validation, TypeORM connection, /api/health, docker compose."
- "Implement the database exactly per the plan: six entities, one initial
  migration with ticket_number sequence (start 10001), the partial unique
  index enforcing at-most-one active ticket per user, unique telegram_update_id,
  and the assistant-settings singleton CHECK."
- "Build the inbox/outbox so no message is ever lost: ON CONFLICT DO NOTHING
  ingest, atomic claims, per-chat ordering, a 15-second sweeper, and a durable
  outbox where every outbound message is stored PENDING before any send."
- "Write the ContextBuilder so ONLY messages of the same ticket_id ever enter
  the AI payload, with a test proving ticket A's text never appears in
  ticket B's payload — isolation by data structure, not by prompt."
- "Do NOT call the real Telegram/OpenRouter APIs yet — leave their config
  slots empty and keep the modules disabled until I provide the credentials."
- "Add WebSocket: when a user opens a ticket from Telegram, the admin must
  see and answer it in the panel the same moment — Socket.IO with JWT for
  the panel, polling only as fallback."

Verification performed before each commit
-----------------------------------------
- `npm run build` clean, `npm test` (92 unit) and `npm run test:e2e`
  (13 scenarios on real PostgreSQL) green — see docs/test-report.md.
- Functional webhook runs with simulated Telegram updates (dedup, ticket
  creation, outbox failures with clear reasons while tokens are empty).
- Live browser session: login, dashboard, tickets, bidi-safe Persian
  conversation, live websocket message arrival without reload (screenshots
  in docs/screenshots/).
- Secret scan of the working tree and full git history before packaging
  (Telegram token pattern, OpenRouter key pattern, fine-grained PAT pattern).

Model used at runtime
---------------------
- None yet — OPENROUTER_API_KEY is intentionally empty; the assistant replies
  with a fixed fallback message. The runtime model will be recorded here when
  the owner supplies the key (default seeded model: `openrouter/auto`).
